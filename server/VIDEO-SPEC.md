# «Привязать видео» → «Загрузить видео» — контракт (06.10.2026)

> **Действует механика v2 — раздел 10** (загрузка видео с выбором аккаунта,
> TikTok и YouTube, выплата в момент зачёта, резерв бюджета, лидерборд).
> Всё про окно подсчёта (`VID_WINDOW_DAYS`) и выплату в конце окна ниже —
> история: **заменено разделом 10**.

Владелец: вместо «Сдать работу» — «Привязать видео». Блогер вставляет ссылку на
ролик из своего ПОДТВЕРЖДЁННОГО TikTok; сайт сам берёт данные ролика (просмотры,
лайки, комментарии, репосты), пишет «Подключено». Данные обновляются каждый
день. Ролик проверяется на накрутку — подозрение уходит владельцу (админу).
Рекламодатель проверяет интеграцию: «всё верно» → видео засчитано и считает
просмотры; «есть проблема» + причина → сразу владельцу, решает он.

Источник правды — сервер. Просмотры НИКОГДА не приходят от клиента.

## 1. Правила

> Площадки (только TikTok), окно подсчёта и выплата в конце окна — **заменено разделом 10**.

- Площадка: только TikTok (у оффера в `platforms` есть `tt`/`tiktok`, либо
  площадки не заданы). Для остальных площадок остаётся старая «Сдать работу».
- Ролик должен:
  1. принадлежать подтверждённому TikTok-каналу блогера — доказательство:
     `POST /v2/video/query/` с его токеном возвращает этот id (TikTok сам
     отдаёт только ролики владельца токена);
  2. быть опубликован ПОСЛЕ создания оффера (`create_time*1000 >= camp.createdAt − 10 мин`);
  3. для видеоформатов — не короче `camp.minDuration || camp.videoMinSec` (если задано);
  4. не быть привязан ни к какому другому заданию (уникален по video_id).
- Блогер подтверждает галочкой «В видео есть реклама из этого задания».
- Окно подсчёта: `VID_WINDOW_DAYS` (env, по умолчанию 7) суток с момента зачёта
  (`approved_at`). Пока окно открыто — данные обновляются раз в сутки, сумма
  растёт. В конце окна сервер делает финальный замер и ПЛАТИТ САМ.
- Сумма (`earned`):
  - `payMode === 'fixed'`: `fixedPrice`, если `minViews` не задан или
    `views >= minViews`; иначе 0;
  - иначе (за просмотры): `floor(views * rate / 1000)`, сверху `maxPayout || payMax`
    (если задан), снизу 0; если задан `minViews` и `views < minViews` → 0.
  - Не больше остатка заморозки `camp:<campId>` (`deals.amount − deals.paid`).
- Выплата — из заморозки бюджета `camp:<campId>` тем же движением, что
  `/api/deals/release`: `hold` рекламодателя −sum, `available` блогера +sum,
  `payDeal`. Ключ операции `sysKey('vidpay', rowId)` → повтор безопасен.
- Заморозка выплаты: если у ролика `risk_hold = 1` (накрутка) или открыт спор
  (`openDisputeFor(camp:<id>, blogger)`) — окно может закончиться, но выплата
  ждёт решения владельца.

## 2. Статусы строки `task_videos.status`

> `active` «считаем просмотры в окне» и `paid` «окно закрыто» — **заменено разделом 10.2**.

| статус     | значение | кто переводит |
|------------|----------|---------------|
| `review`   | привязано, ждёт проверки рекламодателем | bind |
| `active`   | засчитано, считаем просмотры в окне | рекламодатель «всё верно» / владелец «засчитать» |
| `rejected` | рекламодатель указал проблему, ждёт решения владельца | рекламодатель |
| `declined` | владелец решил не засчитывать (выплаты нет) | владелец |
| `paid`     | окно закрыто, выплачено `paid` ₽ (может быть 0) | сервер |
| `removed`  | ролик удалён/скрыт (дважды подряд не вернулся из query) | сервер |
| `revoked`  | блогер отозвал доступ TikTok / отвязал канал | сервер |

`unbind` — блогер сам удаляет привязку, только в `review` (ошибся ссылкой).

## 3. Таблицы (server.js, рядом с channels/channel_stats)

```sql
CREATE TABLE IF NOT EXISTS task_videos (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  camp_id TEXT NOT NULL, owner_id INTEGER NOT NULL, blogger_id INTEGER NOT NULL,
  platform TEXT NOT NULL DEFAULT 'tiktok', external_id TEXT NOT NULL,   -- open_id канала
  video_id TEXT NOT NULL,                       -- СТРОКА: 19 цифр > 2^53
  url TEXT, handle TEXT, title TEXT, duration INTEGER, posted_at INTEGER,  -- posted_at мс
  views INTEGER DEFAULT 0, likes INTEGER DEFAULT 0, comments INTEGER DEFAULT 0, shares INTEGER DEFAULT 0,
  stats_at INTEGER, miss INTEGER DEFAULT 0,      -- miss: подряд не вернулся из query
  status TEXT NOT NULL DEFAULT 'review',
  review_note TEXT, reviewed_at INTEGER, approved_at INTEGER,
  decision TEXT, decision_note TEXT, decided_at INTEGER,
  risk INTEGER, risk_level TEXT, risk_why TEXT, risk_at INTEGER, risk_hold INTEGER DEFAULT 0,
  earned INTEGER DEFAULT 0, paid INTEGER DEFAULT 0, paid_at INTEGER,
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  UNIQUE(platform, video_id)
);
CREATE INDEX IF NOT EXISTS task_videos_camp ON task_videos(camp_id);
CREATE INDEX IF NOT EXISTS task_videos_blogger ON task_videos(blogger_id);
CREATE TABLE IF NOT EXISTS task_video_stats (
  video_row INTEGER NOT NULL, day TEXT NOT NULL,   -- 'YYYY-MM-DD' по UTC
  views INTEGER, likes INTEGER, comments INTEGER, shares INTEGER, at INTEGER,
  PRIMARY KEY(video_row, day)
);
```

## 4. Ручки (JSON, вход через обычную сессию `auth(req)`)

> `windowEndsAt`, «ok → active, окно пошло», тексты ошибок bind — **заменено разделом 10.3**.

Объект ролика наружу (`vidDTO`), одинаковый для всех ручек:
```
{ id, campId, bloggerId, ownerId, platform:'tiktok', videoId, url, handle, title,
  duration, postedAt, views, likes, comments, shares, statsAt,
  status, reviewNote, reviewedAt, approvedAt, decision, decisionNote, decidedAt,
  windowEndsAt,            // approved_at + VID_WINDOW_DAYS сут (или null)
  earned, paid, paidAt,
  risk, riskLevel, riskWhy: [строки], riskHold,   // riskWhy блогеру НЕ отдаём (только level)
  cover,                   // свежая обложка из последнего query/oembed или null (не хранить надолго)
  player: 'https://www.tiktok.com/player/v1/<videoId>',
  history: [{day, views, likes, comments, shares}]   // только в /api/tasks/video (одна строка)
}
```

- `POST /api/tasks/video/bind {campId, url, agree:true}` → `{ok, video:vidDTO}`
  Ошибки (`{error, code}`; текст — по-русски, готов для показа):
  - 401 нет входа; 429 часто (лимит `vbind` 10/мин);
  - 400 `bad_url` «Это не ссылка на видео TikTok»; 400 `agree` «Подтвердите, что в видео есть реклама из задания»;
  - 404 `no_camp` «Задание не найдено»; 409 `camp_closed` «Задание уже не принимает видео»;
  - 409 `own_camp` «Это ваше задание»; 409 `not_tiktok` «В этом задании нет TikTok»;
  - 409 `no_channel` «Сначала подтвердите свой TikTok в профиле» (нет строки channels/channel_tokens);
  - 409 `token` «Доступ к TikTok истёк — переподключите аккаунт»;
  - 409 `scope` «Переподключите TikTok и разрешите доступ к роликам» (scope_not_authorized / scope_permission_missed);
  - 404 `not_found` «Видео не найдено — проверьте ссылку» (короткая ссылка ведёт на главную, oEmbed 400);
  - 409 `not_yours` «Это видео не с вашего подтверждённого TikTok»;
  - 409 `too_old` «Видео опубликовано раньше, чем появилось задание»;
  - 409 `too_short` «Видео короче N сек — так в условиях задания»;
  - 409 `taken` «Это видео уже привязано к заданию»;
  - 502 `tiktok` «TikTok сейчас не отвечает — попробуйте через минуту».
  Владелец оффера: `q.syncGet.get('camp', campId).a_id`, данные оффера — `JSON.parse(row.data)`
  (поля как в клиенте: status, platforms, rate, payMode, fixedPrice, maxPayout|payMax,
  minViews, minDuration|videoMinSec, createdAt, deadline, name).
  После вставки: снимок дня, оценка накрутки (п. 6), уведомления (п. 7).
- `GET /api/tasks/videos?campId=` →
  - если я владелец оффера: все строки оффера;
  - иначе: мои строки (как блогер), по офферу или все.
  Без campId: мои как блогер + все по моим офферам. Ответ `{ok, videos:[vidDTO]}` (без history).
- `GET /api/tasks/video?id=` → одна строка с `history` (участник или админ).
- `POST /api/tasks/video/review {id, ok:true}` | `{id, ok:false, reason}` — только владелец
  оффера, только из `review`. ok → `active`, `approved_at=now`. Нет → `rejected`,
  `review_note` (5–500 символов), `tgAlert` владельцу (п. 7).
- `POST /api/tasks/video/unbind {id}` — блогер, только `review`.
- `POST /api/tasks/video/refresh {id}` — участник; не чаще раза в 10 минут на ролик
  (иначе `{ok:true, video, fresh:false}`), только для `review|active`.

Админ (`isAdmin`, `adminLog`):
- `GET /api/admin/task-videos?status=queue|rejected|risk|active|all` →
  `{ok, videos:[vidDTO + {campName, ownerEmail, ownerName, bloggerEmail, bloggerName, channelTitle, channelRiskLevel, history}]}`;
  `queue` = `rejected` ∪ (`risk_hold = 1`).
- `POST /api/admin/task-videos/decide {id, decision:'count'|'decline', note}` →
  `count`: снять `risk_hold`; из `rejected` → `active` с `approved_at=now`;
  `decline`: → `declined`. Записать decision/decision_note/decided_at, уведомить обе стороны.
- В `/api/admin/overview` добавить поле `видео_на_решении` (= queue count) для значка.

## 5. Фоновый круг `vidSyncRound` (раз в 30 мин, `.unref()`, защита `vidSyncBusy`)

> Финальный замер в конце окна и выплата кругом — **заменено разделом 10** (круг платит только засчитанные, которые ждут: 10.4).

- Берёт строки `status IN ('review','active')` с `stats_at < now − 20 ч`
  (или окно активной кончилось), группирует по (blogger_id, external_id),
  по 20 id на запрос `video/query` с токеном канала (`ttAccess`). Не больше
  ~200 роликов за круг.
- Обновляет цифры, пишет снимок дня (UPSERT по day), считает накрутку.
- Ролик не вернулся → `miss+1`; при `miss >= 2` → `removed` + уведомление обеим
  сторонам. Нет токена/scope → не трогать цифры, `tgAlert('vid:token:'+blogger)`.
- `active` с истёкшим окном → финальный замер (уже сделан выше) →
  `earned` → выплата (п. 1) → `paid`, `paid_at`; если `risk_hold`/спор — не платить,
  `tgAlert('vid:hold:'+id)` раз в сутки.
- Тот же круг можно вызвать в тестах: экспорт/ручка `POST /api/admin/task-videos/sync` (админ).

## 6. Накрутка — `quality.assessVideo(cur, prevDays, channel)` в quality.js

Вход: текущие цифры ролика, снимки предыдущих дней, база канала
(`channel_stats` последняя строка: med_views, followers, er_likes; `channels.risk_level`).
Выход как у `assess`: `{risk 0..100, level ok|watch|risk|bad, reasons[] по-русски}`.
Признаки (пороги в THRESHOLDS, дополнить):
- лайков на просмотры < `erLikesDead` при views ≥ 2000;
- нет комментариев и репостов при views ≥ 5000;
- просмотров > 25× медианы канала И > 10× подписчиков при низких лайках;
- суточный прирост просмотров > 5× прошлого прироста и > 20 000, а лайков прибавилось
  непропорционально мало (доля новых лайков < 0,3 от обычной);
- канал сам в `risk_level = bad` (+15).
`level >= risk` → `tgAlert('vid:risk:'+id+':'+level, …)` с причинами и ссылкой.
`level === 'bad'` → `risk_hold = 1` (выплата ждёт владельца).

## 9. Разбор после аудита (06.10.2026)

> Пункты «Резерв бюджета» (потолок вместо оценки), «Нет финального замера», «Очередь круга» (финальный замер) и «Видно в очереди» (кончившееся окно) — **заменено разделом 10**. Снимок условий, нехватка денег, решение о накрутке, отвязка канала, автозачёт — действуют.

Поверх п. 1–8; где расходится — действует этот раздел.

- **Снимок условий.** При привязке в `task_videos.terms` пишется JSON
  `{payMode, rate, fixedPrice, cap, minViews}`. `earned` считается только по
  снимку; у старых строк без снимка он один раз берётся из конверта оффера и
  сразу записывается. `earned` — заработок блогера, остатком заморозки НЕ
  срезается (п. 1 «не больше остатка» отменён).
- **Резерв бюджета.** `POST /api/deals/refund` по `camp:<id>` (не оператор) →
  409 `{code:'videos_live', error:'По офферу есть видео на проверке или в подсчёте — вернуть бюджет можно после выплат по ним'}`,
  пока у оффера есть строки `review|active|rejected`.
  `POST /api/deals/release` по `camp:<id>` → 409 `{code:'videos_reserved', reserved, free, error}`,
  если сумма больше `остаток − резерв`; резерв = Σ max(earned, потолок) − paid
  по живым строкам (потолок — `fixedPrice` или `cap`, если задан).
- **Нехватка денег при выплате.** Платим, что есть; строка остаётся `active`
  с `pay_hold = 1` и `pay_why` («В заморозке кампании не хватило денег:
  недоплачено N ₽»), `paid` может быть больше 0 при `status = active`.
  Блогеру — «заработано N ₽ … задерживается»; «по условиям задания выплаты
  нет» — только при `earned = 0`. Доплата после решения владельца — ключ
  `sys:vidpay:<id>-<paid>`.
- **Решение «засчитать» и накрутка.** `decided_views` — просмотры в момент
  решения о накрутке (если `risk_hold` был). Новая плохая оценка не ставит
  паузу, пока `views ≤ decided_views × 2`. «Засчитать» возвращённый
  рекламодателем ролик от накрутки не освобождает.
- **Нет финального замера.** Через 72 ч после окна без замера сервер НЕ
  платит сам: `pay_hold = 1`, `pay_why` «Нет финального замера: доступ к
  TikTok потерян» (или «…ролик не вернулся из TikTok», если был промах),
  очередь владельца, тревога один раз. «Засчитать» после этого — выплата по
  последнему замеру. Ролик с готовым финальным замером (`stats_at` позже конца
  окна) больше не опрашивается.
- **Отвязка канала** (сам, владелец, канал пропал) снимает в `revoked` только
  `review`; `active` остаются. Обе стороны получают уведомление. Владелец может
  решить по `revoked`: `count` → `active`, `approved_at = now`, `frozen = 1`
  (не опрашивается, платится по текущим цифрам).
- **Очередь круга.** `last_try_at` — каждая попытка освежить; `vidDue` и
  выплаты идут по нему. Строки на паузе (`risk_hold`/`pay_hold`) в выплаты не
  попадают. Промах считается не чаще раза в 20 ч (`last_miss_at`). Ручное
  «Обновить» — не чаще раза в 10 мин по `last_try_at`.
- **Тревога о доступе** (`vid:token`) — раз в сутки на блогера, вместе с
  письмом блогеру «Переподключите TikTok».
- **Повторы.** Отвязка — 5 в час. Письмо рекламодателю о том же ролике в том
  же задании — раз в сутки.
- **Автозачёт.** `review` старше `VID_AUTO_ACCEPT_H` (по умолчанию 72) →
  `active`, `decision = 'auto'`, обеим сторонам «Рекламодатель не ответил за
  3 дня — видео засчитано автоматически». В ответе круга — `autoAccepted`.
- **Видно в очереди.** `queue` и `видео_на_решении` включают `pay_hold = 1` и
  `active` с кончившимся окном и открытым спором.
- **Площадки.** TikTok — если `tt`/`tiktok` есть в `platforms` ИЛИ
  `platformsList` (список, строка или объект `{tt:true}`), либо оба пусты.
- **Новые поля `vidDTO`:** `payHold` (всем), `holdReason` (не блогеру; текст
  `pay_why`), `disputeHeld` (всем; `active` и открыт спор по заданию).
- **Новые колонки `task_videos`:** `terms`, `pay_hold`, `pay_why`,
  `decided_views`, `last_try_at`, `last_miss_at`, `frozen`.

## 10. Механика v2 (как в More Views): загрузка видео, выбор аккаунта, YouTube, выплата в момент зачёта, резерв

Действует с 06.10.2026 и **заменяет** окно подсчёта (`VID_WINDOW_DAYS`) и
выплату в конце окна из разделов 1, 2, 4, 5, 8 и 9. Где разделы выше
расходятся с этим — действует этот раздел.

Владелец: «в задании при вступлении кнопка ЗАГРУЗИТЬ ВИДЕО — блогер выбирает
аккаунт, на котором есть это видео, система смотрит, что видео есть на этом
аккаунте — и оно отправляется; если нет — пишет причину». Образец механики —
More Views (кабинет, договор с креатором, оферта заказчика).

### 10.1. Правила

- **Где.** Кнопка «Загрузить видео» — во ВСЕХ заданиях после вступления,
  любого формата (clips, banners, ugc, other). Исключение — оффер, где площадки
  заданы и среди них нет ни TikTok, ни YouTube: там остаётся «Сдать работу».
  ФОРМАТ оффера сервер не проверяет вовсе.
- **Когда.** Блогер сам решает, когда отправить — «когда готов
  зафиксировать просмотры». Сервер берёт ролик с выбранного аккаунта и цифры.
  Задан `minViews`, а у ролика меньше → отказ `few_views`.
- **Проверка.** Рекламодатель: «Всё верно — засчитать» или «Есть проблема» +
  причина (→ сразу владельцу). Молчит `VID_AUTO_ACCEPT_H` (72) часа —
  засчитано само (`decision = 'auto'`). Решение владельца по спорным — как
  раньше: засчитать / не засчитывать.
- **Засчитано = оплачено сразу.** В момент зачёта (рекламодатель, автозачёт,
  владелец) — один свежий запрос к площадке и одна выплата:
  `views = max(submit_views, свежие просмотры)`, сумма по снимку `terms`
  (`fixed` → `fixedPrice` при `views ≥ minViews`; иначе
  `floor(views × rate / 1000)`, сверху `cap`, ниже `minViews` → 0), не больше
  остатка заморозки `camp:<id>`. Деньги — `dealPayMoves` под ключом
  `sysKey('vidpay', rowId)` (доплата после паузы — `vidpay:<id>-<paid>`).
  Статус → `paid`, поля `paid`, `paid_at`, `paid_views`, `earned`.
  - свежий замер не удался из-за **сбоя площадки** (коды `tiktok` / `youtube`:
    5xx, таймаут, нет связи, сбой Google при обмене доступа) → платим по
    последним цифрам, если им ≤ 24 ч; иначе `pay_hold = 1`,
    `hold_kind = 'measure'`, «Нет свежего замера: …» и повтор в круге (не чаще
    раза в 20 мин); на 3-й неудаче подряд — по последним цифрам, `pay_note`
    «Оплачено по последнему замеру от …» и тревога владельцу;
  - свежий замер не удался из-за **доступа** (`token`, `scope`, `no_channel`:
    блогер отвязал канал или отозвал доступ, канал отключил владелец) → по
    последним цифрам НЕ платим (иначе ролик можно удалить и закрыть доступ):
    `pay_hold = 1`, `hold_kind = 'access'`, причина «Нет доступа к … /
    …-канал блогера отвязан», ролик — в очереди владельца. Его «засчитать»
    платит по цифрам на момент решения; круг повторяет замер не чаще раза в
    3 часа и платит сам, когда блогер переподключит канал (ролика нет →
    `removed`). С `YT_API_KEY` при отвязанном YouTube-канале ролик проверяется
    ключом: удалён или закрыт → `removed`;
  - ролик не вернулся при свежем замере (удалён, скрыт, закрыт, «по ссылке»)
    → `removed`, без выплаты (одного промаха достаточно: доступ ответил, а
    ролика нет);
  - накрутка: `quality.assessVideo` на свежих цифрах; «очень похоже» →
    `risk_hold`, выплата ждёт владельца; его «засчитать» платит по цифрам на
    момент решения, «не засчитывать» → `declined`;
  - открытый спор по заданию → ждёт (`disputeHeld`), круг повторяет;
  - денег в заморозке меньше суммы → платим, что есть, остаток —
    `pay_hold`, `hold_kind = 'money'`, ждёт владельца (как в разделе 9).
- **Просмотры после выплаты в зачёт не идут.** Оплаченный ролик ещё
  `VID_TRACK_DAYS` (30) суток с публикации обновляется раз в сутки — только
  для показа (`views`), `paid_views` и `paid` не меняются.
- **Резерв бюджета («В резерве»).** При загрузке ролику резервируется оценка
  по просмотрам на момент загрузки (`reserved`, по `terms`, с `cap`). Резерв
  ролика = большее из `reserved` и оценки по текущим просмотрам (пока не
  оплачен), после частичной выплаты — недоплата (`vidHoldOf`). Свободно =
  `(amount − paid)` заморозки − Σ резервов роликов `review | rejected |
  active`. Свободно ≤ 0 → отказ `budget`. Ролик стоит больше, чем свободно,
  → принимается, но в снимок `terms` пишется `limit` = свободный остаток:
  оценка, резерв и выплата за ролик — не больше него (`budgetCap` в
  `vidDTO`, приложение говорит «больше за это видео не заплатят»). Так
  «В резерве» не выходит за бюджет. Резерв снимается выплатой, отказом,
  удалением, отвязкой. Возврат остатка (`/api/deals/refund`, им же
  «Завершить задание») — 409 `videos_live`, пока есть такие ролики; ручная
  выплата (`/api/deals/release`) — не больше свободного (`videos_reserved`).
- **Один ролик — одна выплата:** `UNIQUE(platform, video_id)`.
- **Сроки.** Ролик, вышедший раньше оффера (−10 мин) — `too_old`; после
  `deadline` (+10 мин) — `too_late`; срок датой без времени (`ГГГГ-ММ-ДД` из
  шторки «Условия задания») — это конец того дня по Москве (`vidDeadline`).
  После срока задания загрузить можно
  ролик, вышедший ДО срока (блогер сам решает, когда фиксировать
  просмотры), пока оффер `active` и в заморозке есть деньги. Мин. длина
  (`minDuration | videoMinSec`) — `too_short`.
- **Обновление цифр.** Раз в сутки (порог 20 ч, круг каждые 30 мин): `review`
  (рекламодатель видит рост, проверка накрутки), `active` с паузой (накрутка,
  деньги, спор) и `paid` до `VID_TRACK_DAYS`. Засчитанные без паузы и с паузой
  `measure` / `access` замеряет сама выплата. У `paid` порог — от последней
  попытки (`last_try_at`), а не от удачного замера, и при мёртвом доступе
  тревог и «переподключите» нет: денег на кону уже нет.

### 10.2. Статусы для приложения

| статус | значение |
|---|---|
| `review` | загружено, ждёт рекламодателя; резерв держится |
| `rejected` | рекламодатель указал проблему — решает BloggerPay |
| `active` | засчитано, но выплата ждёт: всегда вместе с `riskHold`, `payHold` или `disputeHeld` (или на миг между зачётом и выплатой) |
| `paid` | выплачено `paid` ₽ за `paidViews` просмотров |
| `declined` | владелец не засчитал |
| `removed` | ролика нет на площадке (до зачёта — два промаха с промежутком в сутки, при зачёте — один) |
| `revoked` | канал отвязан до проверки |

### 10.3. API

**`POST /api/tasks/video/bind`** `{campId, url, agree:true, platform?:'tiktok'|'youtube', account?:'<external_id>'}`
→ `{ok, video}`; ошибка `{error, code, platform?}` (+ `views`, `minViews` у `few_views`).

- Площадку определяет ССЫЛКА. TikTok — как раньше (`ttLinkOf`, короткие
  раскрываются). YouTube — только `https`, хосты `youtube.com`,
  `www.youtube.com`, `m.youtube.com`, `youtu.be`, без логина и порта в
  адресе; `/watch?v=ID`, `/shorts/ID`, `/live/ID`, `/embed/ID`,
  `youtu.be/ID`; `ID = [A-Za-z0-9_-]{11}`. Текст вокруг и точка в конце
  фразы допустимы, `https://` можно не писать. По YouTube-ссылке сервер
  никуда не ходит — id достаётся разбором.
- `platform` синонимы: `tt` = tiktok, `yt` = youtube.
- Площадки оффера — `vidCampAllows(camp, platform)`: объединение
  `platforms` и `platformsList` (строка `'tt,yt,tg'`, массив, объект
  `{tt:true}`), без них — поле `platform`; синонимы tt/yt/tg/ig/inst. Не
  заданы → TikTok и YouTube.
- `account` → только этот подтверждённый канал ЭТОГО блогера на ЭТОЙ
  площадке; владение проверяется только по нему. Без `account` — перебор
  всех каналов площадки.
- YouTube: `GET {YT_API_BASE}/youtube/v3/videos?part=snippet,statistics,contentDetails,status&id=ID`.
  `YT_API_KEY` задан → параметр `key`; иначе — доступ выбранного канала из
  `channel_tokens` (`ytAccess`, refresh на `{YT_OAUTH_BASE}/token`).
  Владение: `items[0].snippet.channelId === external_id`. Цифры:
  `views = viewCount`, `likes = likeCount`, `comments = commentCount`,
  `shares = 0`, длительность из ISO 8601, `posted_at = publishedAt`,
  обложка `thumbnails.high|medium|default`, ссылка
  `https://www.youtube.com/shorts/ID` (shorts) или `…/watch?v=ID`, `handle` —
  ник канала (`customUrl` без `@`) или `channelTitle`.
- Подтверждение YouTube (`GET /api/verify/start`) — `access_type=offline`
  (`prompt=select_account consent` был и раньше): Google отдаёт refresh.
  Вход через Google (`/api/auth/google/start`) не тронут.

загруженный ролик (`taken`) — ответ без запроса к площадке; ответ

квоты (дальше `yt_quota`), остальное — запас под замеры при зачёте.

записью это проверяется ещё раз (`no_channel` / `no_account`, `camp_closed`).

**`GET /api/tasks/video/accounts`** (вход) →
`{ok, accounts:[{platform, id, handle:'@…'|'', title, avatar (только https), ready, why:''|'token'}]}` —
свои подтверждённые каналы TikTok и YouTube. `ready = false` — спросить
площадку нечем (доступ протух, а refresh или ключей нет); с `YT_API_KEY`
YouTube-канал готов всегда. Токены не отдаются.

**Участники.** Таблица `task_members(camp_id, user_id, joined_at, left_at, UNIQUE(camp_id, user_id))`.
- `POST /api/tasks/join {campId}` → `{ok, already, joinedAt}`; своё задание —
  409 `own_camp`; оффер не `active` — 409 `camp_closed` «Задание сейчас не
  принимает участников»; повтор — `already:true`. Лимит 30/мин.
- `POST /api/tasks/leave {campId}` → `{ok, left}` (`left_at`); вернуться —
  тем же `/join`.
- `bind` вписывает блогера в участники сам. При запуске сервера все, кто уже
  загружал видео, переносятся в участники (`INSERT OR IGNORE`).

**`GET /api/tasks/board?campId=&offset=&limit=&sort=earned|views`** (вход; видит любой
вошедший) →
```
{ ok, campId, sort,
  members,              // участников без left_at
  videos, views,        // ролики review | rejected | active | paid и их просмотры
  paid, reserved, budget, left,   // из заморозки: выплачено, в резерве, сумма, свободно
  leaders: [{rank, name, handle, platform, avatar, card, me?, videos, views, earned}],   // топ-50
  participants: [{rank, name, handle, platform, avatar, card, me?, videos, joinedAt}],    // больше видео — выше
  offset, limit (≤ 100, по умолчанию 100), more,
  me: {rank|null, videos, views, earned, joined, owner} }
```
Порядок лидерборда — как у More Views (решение владельца 06.10): по
умолчанию (`sort=earned`) «по сумме выплаты» → просмотры → кто раньше
загрузил; `sort=views` — просмотры роликов `review | rejected | active | paid`
→ `earned` → кто раньше (переключатель). `me.rank` — в выбранном порядке.
Участники — у кого больше роликов в задании, выше; при равенстве — кто
раньше вступил. `name` — имя из
профиля (до 40 знаков; почта вместо имени и номер Телеграма из имени по
умолчанию не показываются). `handle`/`platform`/`avatar` — канал самого
смотримого ролика в задании, у участника без роликов — первый подтверждённый
канал. Номеров аккаунтов в строках нет: для кнопок «Профиль» и «Чат» —
`card`, id открытой карточки в каталоге (её и так видят все в `/api/cards`;
нет карточки — `''` и кнопок нет), свою строку сервер отмечает `me: true`.
Только автору задания (`me.owner`) в строках приходит `uid` — чтобы
написать участнику без карточки (номера тех, кто загружал ролики, он и так
видит в `/api/tasks/videos`). Ни почты, ни внешних id каналов. Кэш на оффер — 60 с,
сбрасывается при любом изменении в задании (загрузка, зачёт, выплата,
вступление, выход).

**`vidDTO`** — к прежним полям: `platform` (`tiktok|youtube`), `player`
(YouTube — `https://www.youtube.com/embed/ID`), `submitViews`, `paidViews`,
`reserved` (₽, резерв ролика), `budgetCap` (₽ или null — предел из остатка
бюджета при загрузке), `payNote` (не блогеру). `earned` до выплаты —
сколько ролик стоит сейчас по условиям, после — начислено. `windowEndsAt`
оставлен для старых приложений и равен `approvedAt`. Для YouTube `cover` —
постоянная `i.ytimg.com/vi/ID/hqdefault.jpg`.

**`POST /api/tasks/video/review`** → `{ok, settle:'paid'|'held'|'removed'|'fail', paid, video}`.
**`POST /api/admin/task-videos/decide`** → `{ok, settle, video}`.
**`POST /api/tasks/video/refresh`** — `review`, `active` и `paid` (до
`VID_TRACK_DAYS` с публикации; только показ).
**`GET /api/admin/task-videos?status=`** — `queue | rejected | risk | review | active | paid | all`.
`queue` и `видео_на_решении`: `rejected`, `risk_hold`, `pay_hold` кроме
`hold_kind = 'measure'` (его повторяет круг; `access` — в очереди, круг тоже
пробует, но реже), `active` с открытым спором.

Уведомления блогеру при зачёте не рекламодателем (автозачёт, решение
владельца) — одно: о выплате («Видео засчитано — N ₽ на балансе», причина
зачёта — строкой в том же тексте), а если денег пока нет — о самом зачёте.

### 10.4. Одна дорога денег

`vidPayout(id, {noMeasure})` → `vidPayoutRun` → `vidMeasure` (свежий замер)
→ `vidSettle` (база выплаты фиксируется ОДИН раз в `paid_views`/`earned`,
деньги — `moneyOp` + `dealPayMoves`). Сюда сходятся: «всё верно»
рекламодателя, автозачёт, решение владельца (из `rejected` — со свежим
замером; снятая пауза и `revoked` — по цифрам на момент решения) и круг
(`vidPayDue`: засчитанные без паузы, повтор «нет замера» и «нет доступа», снятый спор,
старые строки `active` из времён окна). Защита от двойной выплаты: ключ
`sys:vidpay:<id>` + замок `vidPaying` на процесс + статус в той же транзакции.

### 10.5. Колонки и настройки

`task_videos`: `submit_views`, `reserved`, `paid_views`, `hold_kind`
(`money | measure | access`), `pay_tries`, `pay_note`; в `terms` может быть
`limit`. Новая таблица `task_members`.
`.env`: `YT_API_KEY` (по желанию), `YT_API_BASE`, `YT_OAUTH_BASE` (в проверках
— подделка), `YT_DAILY_UNITS` (10000), `VID_TRACK_DAYS` (30), `VID_AUTO_ACCEPT_H` (72).
`VID_WINDOW_DAYS` больше не читается.
