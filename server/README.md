# BloggerPay — сервер-касса

Это этап 3 плана запуска: деньги переезжают из браузера туда, где
пользователь их не может тронуть. Пока сервера не было, баланс
переписывался из консоли за три строки — теперь нет.

## Как это устроено

Три правила, на которых держится вся касса:

1. **Баланс не хранится.** Он считается как сумма журнала операций
   (`ledger`). Разойтись двум числам нельзя — второго числа нет.
2. **Журнал только растёт.** Строки не правятся и не удаляются. Отмена —
   это новая встречная запись.
3. **Одна операция проводится один раз.** Каждый денежный запрос несёт
   `opKey`. Повтор с тем же ключом (двойное нажатие, обрыв сети) вернёт
   старый результат и денег не тронет.

Деньги лежат в двух «корзинах»: `available` (можно распоряжаться) и
`hold` (заморожено под сделку или заявку на вывод).

## Запуск

Нужен Node 22.5+ (встроенный `node:sqlite`). Больше ничего — зависимостей нет.

```bash
cd server
cp .env.example .env      # и заполнить ADMIN_KEY
node server.js
```

Сервер поднимется на порту из `.env` (по умолчанию 8090), база ляжет в
`server/data/bloggerpay.db`.

## Бот с кнопкой «Открыть»

Отдельный процесс, работает независимо от кассы:

```bash
node bot.js
```

Что делает: на `/start` присылает приветствие и синюю кнопку, открывающую
мини-апп, а также ставит постоянную кнопку меню рядом с полем ввода.
Нужны две настройки в `.env` — `BOT_TOKEN` (от @BotFather) и `APP_URL`
(адрес приложения, **только https**).

Работает через длинный опрос, поэтому публичный адрес и вебхук не нужны —
бот запускается где угодно. Одновременно должен быть запущен **только один**
экземпляр: второй Телеграм отклонит с ошибкой 409, бот об этом скажет прямо.

Приглашения доезжают: на `/start r_12345` метка уходит в адрес кнопки
(`?startapp=r_12345`), приложение её читает и засчитывает пригласившего.

**Если Телеграм недоступен с сервера** (в России — обычное дело), бот об
этом честно напишет в консоль. Поднимите прокси и укажите его в `.env`:
`TG_API_BASE=https://адрес-вашего-прокси`.

Чтобы бот жил после перезагрузки — держите его тем же способом, что и
кассу (systemd или pm2), это два отдельных процесса.

## Проверка

```bash
node test-scenario.mjs     # 44 проверки: сделка, вывод, дыры из аудита
node test-partial.mjs      # 11 проверок: бюджет кампании на нескольких блогеров
node test-disputes.mjs     # 13 проверок: раздел спорных денег арбитром
node test-kyc.mjs          # 22 проверки: верификация личности оператором
node test-pay.mjs          # 17 проверок: режимы кассы, предохранители, лимит частоты
node test-verify.mjs       # 31 проверка: ссылка авторизации площадок и защита возврата
node test-bot.mjs          # 13 проверок: разговор бота и кнопка (на заглушке, без Телеграма)
node test-telegram.mjs     # 9 проверок подписи Телеграма (нужен BOT_TOKEN)
```

Первый набор прогоняет всю денежную цепочку по живому серверу и все дыры
из аудита: двойную выплату, отмену заявки после взятия в работу, накрутку
баланса, подмену получателя, гонку параллельных операций. Второй — деление
одного бюджета между исполнителями. Оба можно гонять подряд сколько угодно:
сверка считает разницу за прогон, а не абсолютные суммы по базе.

## Что сервер уже умеет

| Путь | Кто | Что делает |
|---|---|---|
| `POST /api/register`, `/api/login`, `/api/logout` | все | вход; пароль хранится scrypt-хешем, проверяется на сервере |
| `GET /api/me`, `/api/balance`, `/api/ledger` | вошедший | читать свои деньги |
| `POST /api/topup` | вошедший | **тестовое** пополнение; выключается TEST_TOPUP=0 и само — при ключах ЮKassa |
| `GET /api/pay/config` | все | режим пополнения: yookassa / test / off |
| `POST /api/pay/create` | вошедший | создать платёж ЮKassa, вернуть страницу оплаты |
| `GET /api/pay/status` | плательщик | статус платежа; оплаченный зачисляется прямо здесь |
| `POST /api/pay/webhook` | касса | вебхук ЮKassa; телу не верим — статус перечитывается из API |
| `POST /api/deals/hold` | плательщик | заморозить под сделку |
| `POST /api/deals/release` | плательщик | выплатить исполнителю целиком или частью (`amount`); комиссия сделки 0% |
| `POST /api/deals/refund` | плательщик, исполнитель или оператор | вернуть остаток плательщику |
| `POST /api/deals/settle` | только арбитр | разделить заморозку по вердикту |
| `POST /api/withdraw` | вошедший | заявка на вывод (комиссия 4%); только после проверки личности |
| `POST /api/withdraw/cancel` | вошедший | отменить, пока в очереди |
| `POST /api/kyc/submit` | вошедший | анкета и фото паспорта на проверку личности |
| `GET /api/kyc/status` | вошедший | статус своей проверки: queued / approved / rejected |
| `POST /api/auth/telegram` | все | вход из мини-аппа с проверкой подписи |
| `GET /api/verify/start` | вошедший | начать подтверждение канала (вернёт ссылку и метку) |
| `GET /api/verify/callback/:площадка` | площадка | возврат после входа; показывает код, ничего не привязывает |
| `GET /api/verify/pending` | вошедший | дошёл ли человек до конца на площадке |
| `POST /api/verify/confirm` | вошедший | привязать канал по коду со страницы возврата |
| `GET /api/verify/list` | вошедший | какие каналы подтверждены |
| `POST /api/admin/verify/unlink` | оператор | отвязать канал (продали, потеряли доступ) |
| `POST /api/errors` | все | приём ошибок из приложения |
| `GET /api/admin/errors` | оператор | что и у скольких людей ломается |
| `GET /api/admin/withdrawals` | оператор | реестр заявок |
| `POST /api/admin/withdrawals/take`, `/paid`, `/reject` | оператор | вести выплату |
| `GET /api/admin/kyc` | оператор | заявки на проверку личности (без фото) |
| `GET /api/admin/kyc/photo` | оператор | фото документа одной заявки |
| `POST /api/admin/kyc/approve`, `/reject` | оператор | решить по проверке личности (с защитой seenAt) |
| `GET /api/admin/overview` | оператор | сводка и сверка |
| `GET /api/admin/users` | оператор | люди: поиск `q` (имя, почта, номер, Телеграм), фильтр `filter` (blogger, advertiser, kyc, blocked, admin), `limit`/`offset` |
| `GET /api/admin/user` | оператор | один человек: профиль, баланс, журнал денег, проверка личности, каналы, карточки, выводы |
| `POST /api/admin/users/block` | оператор | заблокировать или вернуть (`{userId, blocked, reason}`); владельца нельзя |
| `GET /api/admin/cards`, `POST /api/admin/cards/hide` | оператор | каталог со сводкой карточек; снять с витрины или вернуть |

Оператор опознаётся одним из трёх способов: аккаунт с почтой из `ADMIN_EMAIL`,
сессия-кука `bp_admin` (её выдаёт `POST /api/admin/session` после ОДНОГО ввода
ключа; изменяющие запросы должны нести заголовок `X-Admin-Session: 1`) или
заголовок `X-Admin-Key` со значением `ADMIN_KEY` из `.env`.

## Админ-панель владельца

Откройте **http://<адрес сервера>/admin** (старый адрес `/operator` ведёт
туда же) и введите ключ из `.env` — один раз: дальше сервер держит
сессию 12 часов или до кнопки «Выйти». Если в этом же браузере вы вошли в
приложение почтой из `ADMIN_EMAIL`, ключ не спросят вовсе.

Это **отдельная страница, а не часть мини-аппа**: админ-код не скачивается
пользователям, а каждое действие всё равно проверяет сервер. До 15.09.2026
была ещё «Панель владельца» внутри мини-аппа, но она почти целиком
показывала данные одного браузера — её убрали, всё собрано здесь.

Разделы: **обзор**, **выплаты**, **верификация**, **спорные деньги**,
**пользователи**, **каталог**, **поломки**, **площадки** и **журнал**.

### Пользователи

Все аккаунты сервера: поиск по имени, почте, номеру или Телеграму и
фильтры (блогеры, рекламодатели, ждут проверки, заблокированные,
владельцы). Карточка человека открывается сбоку: баланс и заморозка по
журналу денег, проверка личности с фото, подтверждённые каналы (можно
отвязать канал от всех аккаунтов — если его продали), карточки в каталоге,
выводы и последние движения денег. **Блокировка** сразу закрывает вход,
гасит сессии и убирает человека из каталога и рейтинга; деньги и заявки не
трогает. Владельца заблокировать нельзя.

### Каталог и журнал

Каталог показывает все карточки со сводкой (площадки, подписчики, цена
«от», тематики) — любую можно снять с витрины и вернуть. Журнал записывает
каждое действие в панели: выплаты, отказы, решения по личности и спорам,
блокировки, витрину — и кто их сделал (почта владельца или «сессия
пульта»/«ключ»).

Что там есть:

- очередь заявок с именем, реквизитами, суммой к выплате и комиссией;
- кнопки **взять в работу → выплачено → отклонить**, с подтверждением на
  необратимом шаге и обязательной причиной при отказе;
- вкладки по статусам и обновление раз в 20 секунд;
- **сверка** сверху: внесено − выплачено наружу = столько-то в системе.
  Если равенство разошлось, полоса становится красной и называет сумму
  расхождения. Это проверено подлогом: добавленные в обход операций
  777 ₽ немедленно подняли тревогу.

Порядок работы простой: взять в работу → перевести деньги своим банком по
реквизитам → отметить «выплачено». Пока заявка в очереди, человек может
отменить её сам; после «взять в работу» — уже нет.

### Верификация

Люди, которые хотят выводить деньги, присылают анкету (ФИО и дату
рождения) и фото разворота паспорта — из шага «Проверка личности» перед
выводом. Раздел показывает анкету рядом с фото: откройте фото на весь
экран, сверьте данные и решите — **подтвердить** или **отклонить** с
причиной. Причину человек увидит в приложении и сможет прислать документы
заново. Пока личность не подтверждена, вывод у человека закрыт.

### Спорные деньги

Второй раздел показывает все незакрытые заморозки: сделки и бюджеты
кампаний. Обычно их закрывают сами участники — вмешиваться нужно только
по спору.

Раздел делит **остаток** заморозки: доля исполнителю в процентах, остальное
возвращается заказчику. Округление сделано вычитанием, поэтому суммы всегда
сходятся ровно, без потерянных копеек. Перед подтверждением показывается
точный расчёт, решение необратимо.

**Почему это здесь, а не в приложении.** Раздел спорных денег требует ключа
арбитра, а его нельзя класть в файл, который скачивает каждый пользователь —
именно так и была устроена прежняя дыра, когда арбитром становился любой,
кто открыл исходный код. Теперь решение принимает только тот, у кого есть
ключ, то есть вы.

### Поломки

Ошибки, которые случились у людей в приложении. Раньше они жили в памяти
вкладки и стирались при перезагрузке: человек видел белый экран, а владелец
не узнавал об этом никогда.

Одинаковые ошибки собраны в одну строку — важно, **что** ломается и у
**скольких людей**. Строка, случившаяся больше чем у одного человека,
подсвечивается: это признак системной поломки, а не случайности. Личных
данных не собирается — только текст ошибки, место в коде и версия.

Приложение отправляет их редко и пачками, повторы за сеанс схлопывает, а
журнал на сервере подрезается, чтобы одна зациклившаяся вкладка не забила
базу.

## Чего ещё нет — и это осознанно

- **Приём платежей — тестовый.** `POST /api/topup` начисляет деньги любому
  вошедшему, без оплаты. Это заглушка для отладки. **Перед боевым запуском
  её убирают** и на её место ставят вебхук платёжного провайдера, который
  начисляет деньги только после реальной оплаты. Форма запроса при этом
  сохранится, менять клиент не придётся.
- **Выплаты проводит человек.** Сервер не отправляет деньги на карты сам —
  он ведёт реестр: оператор видит заявку, переводит деньги своим банком и
  отмечает «выплачено». Автоматические выплаты — отдельная интеграция.
- **Подтверждение каналов готово, но ждёт ключи площадок.** Человек входит
  в свой аккаунт на YouTube или TikTok, и площадка сама сообщает нам, чей
  это канал — в отличие от вставленной ссылки, подделать это нельзя. Токены
  доступа после проверки не хранятся: они нужны один раз, а лежать —
  только увеличивать ущерб от утечки. Ключи берутся в кабинетах
  разработчика (ссылки и адреса возврата — в `.env.example`). Пока их нет,
  кнопка «Подтвердить» честно говорит, что проверка не настроена.
  Телеграм пока не подключён: у него нет такого же входа, там нужен
  бот-администратор канала — отдельная работа.
- **Вход по Телеграму готов, но ждёт токен бота.** Подпись `initData`
  проверяется на сервере по схеме из документации Телеграма: без этого
  любой мог бы представиться кем угодно, потому что строка приходит из
  браузера. Впишите `BOT_TOKEN` из BotFather в `.env` — и кнопка
  «Telegram» на экране входа заработает. Пока токена нет, сервер честно
  отвечает «не настроено», и приложение говорит об этом человеку.

## Правила сделки

Заморозка может назвать **получателя** (`payeeId`). Тогда:

- выплатить можно **только ему** — подменить получателя перед выплатой нельзя;
- **исполнитель тоже может отказаться** от сделки и вернуть деньги. Себе он
  их при этом не заберёт: возврат всегда идёт плательщику.

Это важно для сценария «блогер отказался»: он обычный, а не исключительный,
и требовать ради него оператора было бы неправильно.

## Связь с приложением

В `bloggerpay-1008-v95.html` есть слой `bp-server` — мост. Он появляется,
когда задан адрес сервера (`window.BP_SERVER` или ключ `bp_server_url`).
Наружу отдаёт `window.bpSrv` с теми же операциями. Пока адрес не задан,
приложение работает по-старому, целиком в браузере.

Поверх моста есть слой `bp-money` — фасад: одни и те же операции работают
и локально, и через сервер. Правило у всех перехватов одно: **сначала
сервер, потом местная часть**. Отказ сервера прекращает операцию, и
приложение не покажет выплату, которой не было. Числа баланса после каждой
операции берутся с сервера, поэтому расхождение самолечится.

**Мост личностей.** У приложения свои id, у сервера свои. Связь — поле
`srvId`. Чтобы заплатить блогеру, нужен его серверный id: он едет со
сделкой. Если его нет, приложение честно говорит «блогер не подключён к
серверу», а не делает вид, что заплатило.

**Что уже переведено на сервер** (действия, которые совершает сам
рекламодатель — только его сессия вправе двигать его деньги):

- пополнение;
- заморозка бюджета при отправке заявки;
- выплата блогеру при подтверждении выполнения.

**Почему принятие заявки блогером не переведено.** Сейчас блогер, нажимая
«принять», списывает деньги у рекламодателя. Это работает, только пока оба
сидят в одном браузере — чужой сессией на сервере списать нельзя и не
нужно: в серверном режиме деньги замораживаются раньше, при отправке.

**Заявки на вывод** тоже идут через кассу. Кнопку «Создать заявку» нельзя
перехватить через `window` — обработчик повешен прямой ссылкой на внутреннюю
функцию, поэтому клик ловится в фазе перехвата: сервер спрашивается первым.
Отмена заявки после того, как оператор взял её в работу, отклоняется —
проверено через приложение, деньги не возвращаются.

**Кампании.** У кампании один бюджет и много исполнителей, поэтому на
сервере она живёт как одна заморозка с ключом `camp:<id>`, из которой платят
частями. Запуск кампании замораживает бюджет, приёмка задания выплачивает
блогеру его часть, закрытие возвращает остаток — не весь бюджет.

**Что осталось местным:** бонусы, реферальные начисления и решения по спорам.
Локальный режим при этом работает как прежде — ничего не сломано.

## Тревога в Телеграм: скрытые ошибки летят владельцу

Приложение и так ловит все ошибки (даже проглоченные пустыми `catch`)
и складывает их в базу — раздел «Поломки» у оператора. Теперь каждая
**новая** ошибка ещё и прилетает владельцу сообщением в Телеграм через
того же бота.

Настройка — две строки в `.env`:

```
BOT_TOKEN=...            # тот же бот, что и кнопка «Открыть»
ADMIN_CHAT_ID=...        # числовой id чата владельца (узнать: @userinfobot)
```

Владелец должен один раз нажать Start у бота — иначе Телеграм не даст
боту писать первым. Что приходит:

- 🐞 ошибка на сайте: текст, место в коде, версия, кто словил;
- 💥 сервер споткнулся на запросе (ответ 500) или в обещании;
- 💀 сервер упал (успевает крикнуть перед перезапуском);
- 🚨 сторож денег: раз в 10 минут сверяет журнал; расхождение = тревога.

Против потопа несколько предохранителей: одна и та же ошибка — не чаще
раза в 10 минут; лимиты в час раздельные — до 15 тревог с сайта и до 10
серверных (дальше одно «молчу до конца часа»), причём поток мусора с
сайта не может заглушить серверные тревоги, а «деньги не сходятся»
проходит всегда. Тревога никогда не задерживает ответ пользователю.
Полный список всегда в пульте оператора.

Проверки: `node test-alerts.mjs` — 17 штук на заглушке Телеграма.

## Восстановление пароля: письмо с кодом

Раньше «Забыли пароль?» умело только одно — спросить **текущий** пароль.
Для того, кто его как раз забыл, это не помощь; так было сделано
вынужденно, потому что писем отправить было некому (правка 9.2 аудита).
Теперь почта есть, и это настоящее восстановление.

Как идёт поток:

1. `POST /api/password/forgot` `{email}` — сервер шлёт письмо с
   шестизначным кодом. Ответ **всегда одинаковый**, есть такой аккаунт
   или нет: по ответу нельзя проверить, зарегистрирован ли адрес.
2. `POST /api/password/verify` `{email, code}` — проверка кода, **не
   тратя** его. Нужна экрану ввода кода, чтобы подсветить ошибку сразу.
3. `POST /api/password/reset` `{email, code, password}` — код тратится,
   пароль меняется, **все прежние сессии сбрасываются**, выдаётся новая.

Предохранители: код живёт 10 минут; новый — не чаще раза в минуту и не
больше пяти за час на адрес; пять неверных попыток гасят код. В памяти
хранится не сам код, а его HMAC на случайном секрете процесса.

Настройка — в `.env`:

```
RESEND_API_KEY=re_...                        # resend.com → API Keys
MAIL_FROM=BloggerPay <no-reply@ваш-домен.ru> # адрес на подтверждённом домене
MAIL_REPLY_TO=                               # необязательно
MAIL_DEBUG=                                  # 1 только для отладки, НЕ на бою
```

Про отправителя: `onboarding@resend.dev` годится только для пробы — с
него письма приходят **исключительно** на адрес владельца аккаунта
Resend. Для боя подтвердите свой домен (Resend → Domains, записи SPF и
DKIM) и поставьте адрес на нём, иначе письма пойдут в спам или не дойдут.

`MAIL_DEBUG=1` возвращает код прямо в ответе `/api/password/forgot` —
удобно проверять поток без почты, но на бою это утечка кода. Пусто или 0.

Письмо рисует `mail.js` (`renderCodeEmail`): тёмная карточка в палитре
приложения, код по разрядам в отдельных окошках, срок действия,
предупреждение «никому не сообщайте». Картинок нет — только таблицы и
инлайновые стили, поэтому письмо одинаково выглядит в Gmail, Apple Mail
и Outlook и не ломается с отключёнными изображениями.

В приложении экран восстановления — слой `bp-pwreset` в конце
`bloggerpay-1008-v100.html`: три шага (адрес → код → новый пароль),
шесть окошек с автопереходом и вставкой кода целиком. Слой включается
только когда задан адрес сервера; без сервера «Забыли пароль?» работает
по-старому.

Проверки: `node test-mail.mjs` — 14 штук, писем не отправляет
(поднимает сервер с `MAIL_DEBUG=1` и пустым ключом).
